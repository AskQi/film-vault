## 3. 开发顺序说明

1. **M0 必须先做**，因为码表 seed 与型号库 seed 是 M1 的输入。
2. **M1 是地基**，编号解析一旦有 bug，建档数据全部污染，因此必须先写单测再写页面。
   - 特别注意：**不能全局 `toUpperCase()`**，会破坏小写例外码（`KPdT`）。
3. **M3 是价值核心**，如果时间紧，可以把 M4 的冲洗、归档部分延后。
4. M2 与 M3 可以并行，但需要先有 M1 的型号库。

## 4. 技术风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 全局转大小写破坏小写例外码 | 型号误判、序号错位 | 逐位校验，单测覆盖 `KPdT` vs `KPDT`、`KG2TA07` vs `KG2Ta07` |
| 序号跨 999 后排序错乱 | 最新卷排到最前/后 | 一律按整数 `seq` 排序，禁止按 `serial_txt` 字符串比较 |
| 前缀用满 6199 | 无法继续编号 | 容量远超个人使用量；真需要时 `stock_prefix` 支持追加备用前缀 |
| 站外打印软件归一化大小写 | 小写序号失去语义 | 打印时确保原样输出 7 字符；`KG2Ta07` 的小写 `a` 不能变成 `A` |
| iOS/鸿蒙扫码兼容性 | 无法扫码 | 一开始就用 `barcode-detector` WASM polyfill；M2 首日即三端实测 |
| 没有 HTTPS 导致摄像头不可用 | 扫码功能失效 | 开发用 `localhost`，生产用 Caddy 自动证书 |
| 预置型号有错漏 | 建档数据不准 | 用户逐条可编辑；条码字段留空由用户绑定 |
| SQLite 并发写入 | 单用户场景几乎不会发生 | 开启 WAL；写入走单进程 |
| 折叠屏布局 | 内容被拉伸 | Tailwind 断点，卡片限宽 `max-w-*` |
